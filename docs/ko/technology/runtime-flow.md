# 런타임 흐름: 로그와 Trace

"이 요청이 어느 서비스를 거쳐 어디까지 갔나"는 보안 담당자가 가장 자주 묻는 질문입니다. SADE는 서비스마다 따로 남은 로그 조각을 **같은 요청끼리 이어 붙여** 실제 경로를 복원합니다. 코드에서 찾은 흐름([code2flow](code2flow.md))이 "부를 수 있는 곳"이라면, 여기서 그리는 흐름은 "실제로 부른 곳"입니다.

## 재료

| 입력 | 담긴 정보 | 호출 수 |
|---|---|---|
| Access 로그 | 서비스가 **받은** 요청 | 셈 |
| Application 로그 | 서비스가 **보낸** 요청 (목적지, 방향) | 세지 않음 |
| OpenTelemetry span | 부모·자식 관계, 호스트, DB 접근 | 세지 않음 |

같은 요청이 여러 곳에 기록돼도 호출 수는 받은 쪽에서 한 번만 셉니다. 로그마다 어떤 필드가 있어야 하는지는 [로그 필드 레퍼런스](../connect/schema.md#levels)에 정리했습니다.

## 조각을 잇는 순서

받은 쪽과 보낸 쪽을 아래 순서로 맞춰 봅니다. 앞 단계에서 확정되면 뒤 단계는 보지 않습니다.

<div class="sade-steps" markdown>

1. **Trace.** trace ID가 같고, 받은 쪽(SERVER)의 parent span ID가 보낸 쪽(CLIENT)의 span ID와 같으면 같은 호출입니다. 가장 확실한 방법입니다.
2. **Hop ID.** 한 번의 서비스 간 호출마다 붙는 ID가 같으면 같은 호출입니다.
3. **Request ID.** 같은 request ID이고, 목적지 서비스·메서드·경로가 같고, 30초 안이면 같은 호출로 봅니다.

</div>

- 맞는 후보가 여러 개면 잇지 않습니다. 같은 API로 동시에 들어온 요청끼리 뒤섞이지 않게 하려는 것입니다.
- trace 정보가 서로 다르면 request ID가 같아도 잇지 않습니다.
- 호출자 정보가 없으면 접속 IP를 호출자로 씁니다. 등록된 서비스의 별칭에 그 IP가 있으면 그 서비스가 호출자입니다.

### traceparent만 남은 로그

게이트웨이와 서비스 접근 로그에는 trace 필드 대신 W3C `traceparent` 헤더 하나만 남는 경우가 많습니다.

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                └──────────── trace ID ────────────┘ └─ 부모 span ─┘
```

받은 요청의 `traceparent`에 있는 span은 **나를 부른 쪽의 span**입니다. 그래서 Access 로그에서는 이 값을 trace ID와 parent span ID로 읽습니다. 로그에 trace 필드가 따로 있으면 그쪽을 먼저 씁니다. 일반(Legacy) HTTP 로그에서는 읽지 않습니다. 게이트웨이와 서비스 로그를 request ID로 합치는 기존 동작을 바꾸지 않기 위해서입니다.

### 프록시 뒤의 실제 호출자

게이트웨이 뒤에 있는 서비스 로그의 접속 IP는 대개 게이트웨이 주소입니다. 실제 외부 호출자는 `X-Forwarded-For`의 첫 주소에 있습니다. SADE는 두 값을 따로 남깁니다.

| 값 | 예 | 쓰임 |
|---|---|---|
| `client_ip` | `10.0.4.12` (게이트웨이) | 바로 앞 구간의 호출자, Flows 그룹 |
| `forwarded_for` | `203.0.113.7` | 원래 클라이언트. Call History에 "203.0.113.7 via 10.0.4.12"로 표시 |

IP는 공인 주소도 그대로 남깁니다. 포트만 뗍니다. 보안 담당자가 호출자를 추적해야 하기 때문입니다.

## 두 가지 화면

=== "요청 하나의 경로 (Request flow)"

    Call History나 API 상세 › Calls에서 요청 하나를 고르면, 그 요청에 연결된 기록 지점을 트리로 보여 줍니다.

    - 지점마다 요청·응답의 민감 필드와 검사 범위를 함께 표시합니다.
    - 요청 하나당 최대 1,000개 기록 지점까지 봅니다.
    - 부모 누락, 후보 여럿, 충돌하는 span, 순환은 **Partial**로 이유와 함께 표시합니다.
    - 여러 지점에서 같은 유형의 필드가 보여도 "같은 값이 전달됐다"는 뜻은 아닙니다.

=== "전체 환경 (Flows)"

    여러 요청을 모아 **Clients → Gateways → Hosts → Destinations** 순서로 보여 줍니다.

    - **Clients**: 로그에 찍힌 호출자. IP를 고르면 그 IP의 요청 경로만 펼칩니다.
    - **Gateways**: 배포 정보, 이름, 라우팅 규칙으로 정한 게이트웨이
    - **Hosts**: 수집된 호스트 정보(`host.id`, `k8s.node.name` 등)로 묶은 서버. 정보가 없으면 "Host not observed"
    - **Destinations**: span으로 확인한 PostgreSQL DB, 스캔하지 않은 외부 호스트

    같은 진입 API라도 뒤쪽 흐름이 다르면 다른 그룹으로 나눕니다. 진입 API만 보이고 그 뒤를 이을 기록이 없으면 "Entry API observed"로 표시합니다.

## DB 접근

PostgreSQL 클라이언트 span(`kind: 3`, `db.system.name: postgresql`)이 있으면 어떤 요청이 어떤 DB에 접근했는지 잇습니다. 부모 span이 호출 서비스의 span이면 API 단위로, 없으면 서비스 단위로 연결합니다.

쿼리 문장, 파라미터, 연결 문자열, 결과 행은 저장하지 않습니다. 연산 이름은 SELECT, INSERT 같은 정해진 값만 남깁니다. 오류 상태가 없다고 트랜잭션 성공을 확정하지 않습니다.

## LOG / SPEC / CODE 전환

Flows 화면의 세 버튼은 어떤 자료로 선을 그릴지 고릅니다. 화면만 바뀌고 수집이나 스캔을 다시 하지 않습니다.

| 자료 | 원 (서비스·API) | 선 |
|---|---|---|
| LOG | 로그·span에서 본 API | 실제 호출, 호출자, span 관계, DB 접근 |
| CODE | 코드에 있는 API | 코드의 HTTP 호출(점선), 게이트웨이 라우팅(파선) |
| SPEC | 명세에 있는 API | 없음. 명세에는 누가 부르는지가 없음 |

## 한계

- 대용량 SIEM 소스는 API별 샘플만 원본으로 남기므로, 흐름도 샘플 범위 안에서 보입니다([대용량 SIEM 수집](siem-collection.md)).
- trace가 샘플링되었거나 일부 서비스가 로그를 남기지 않으면 경로가 끊겨 보입니다. 끊긴 곳은 이유와 함께 표시합니다.
- HTTP 로그만으로는 DB 접근이 생기지 않습니다. DB는 span이 있어야 합니다.
- 메시지 큐, gRPC 흐름은 다루지 않습니다.
