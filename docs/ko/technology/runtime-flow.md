# 런타임 흐름 복원

침해 사고를 조사하거나 개인정보 처리 흐름을 점검할 때 보안 담당자는 같은 질문을 합니다. **"이 요청이 어느 서비스를 거쳐 어느 DB까지 갔고, 그 사이에 어떤 개인정보가 오갔나."** 하지만 로그는 서비스마다, 게이트웨이와 DB마다 따로 쌓여 있어서 사람이 손으로 이어 붙이기 어렵습니다.

SADE는 흩어진 로그 조각을 **같은 요청끼리 이어 붙여** 실제 경로를 복원합니다. 코드에서 찾은 흐름([code2flow](code2flow.md))이 "부를 수 있는 곳"이라면, 여기서 그리는 흐름은 "실제로 부른 곳"입니다.

## 재료

모두 로그입니다. SIEM이나 데이터 레이크에 이미 있는 로그를 그대로 씁니다.

| 로그 | 담긴 정보 | 호출 수 |
|---|---|---|
| Access 로그 | 서비스가 **받은** 요청 | 셈 |
| Application 로그 | 서비스가 다른 서비스로 **보낸** 요청 (대상, 방향) | 세지 않음 |
| 애플리케이션 SQL 로그 | 서비스가 실행한 SQL과 그 요청의 ID | 세지 않음 |
| PostgreSQL 로그 (JSON, pgAudit) | DB가 받은 SQL과 접근한 테이블 | 세지 않음 |

같은 요청이 여러 곳에 기록돼도 호출 수는 받은 쪽에서 한 번만 셉니다. 로그마다 어떤 필드가 있어야 하는지는 [로그 필드 레퍼런스](../connect/schema.md#levels)에 정리했습니다.

## 서비스와 서비스를 잇는 순서

받은 쪽과 보낸 쪽 기록을 아래 순서로 맞춰 봅니다. 앞 단계에서 정해지면 뒤 단계는 보지 않습니다.

<div class="sade-steps" markdown>

1. **Trace.** trace ID가 같고, 받은 쪽(SERVER)의 parent span ID가 보낸 쪽(CLIENT)의 span ID와 같으면 같은 호출입니다. 가장 확실한 방법입니다.
2. **Hop ID.** 서비스 간 호출 한 번마다 붙는 ID가 같으면 같은 호출입니다.
3. **Request ID.** 같은 request ID이고, 대상 서비스·메서드·경로가 같고, 30초 안이면 같은 호출로 봅니다.

</div>

- 맞는 후보가 여러 개면 잇지 않습니다. 같은 API로 동시에 들어온 요청끼리 뒤섞이지 않게 하려는 것입니다.
- trace 정보가 서로 다르면 request ID가 같아도 잇지 않습니다.
- **공통 ID가 없으면 시간과 경로가 비슷해도 잇지 않습니다.** 보안 판단에 쓰는 흐름이므로 추측으로 선을 긋지 않습니다.
- 호출자 정보가 없으면 접속 IP를 호출자로 씁니다. 서비스 별칭에 등록한 IP면 그 서비스가 호출자입니다.

### traceparent만 남은 로그

게이트웨이와 서비스 접근 로그에는 trace 필드 대신 W3C `traceparent` 헤더 하나만 남는 경우가 많습니다.

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
                └──────────── trace ID ────────────┘ └─ 부모 span ─┘
```

받은 요청의 `traceparent`에 있는 span은 **나를 부른 쪽의 span**입니다. 그래서 Access 로그에서는 이 값을 trace ID와 parent span ID로 읽습니다. 로그에 trace 필드가 따로 있으면 그쪽을 먼저 씁니다. OpenTelemetry로 계측하고 있다면 이 값을 로그에 같이 찍는 것만으로 충분합니다.

### 프록시 뒤의 실제 호출자

게이트웨이 뒤에 있는 서비스 로그의 접속 IP는 대개 게이트웨이 주소입니다. 실제 외부 호출자는 `X-Forwarded-For`의 첫 주소에 있습니다. SADE는 두 값을 따로 남깁니다.

| 값 | 예 | 쓰임 |
|---|---|---|
| `client_ip` | `10.0.4.12` (게이트웨이) | 바로 앞 구간의 호출자, Flows 그룹 |
| `forwarded_for` | `203.0.113.7` | 원래 클라이언트. Call History에 "203.0.113.7 via 10.0.4.12"로 표시 |

IP는 공인 주소도 그대로 남기고 포트만 뗍니다. 호출자를 추적해야 하기 때문입니다.

## DB 접근 잇기 {#database}

trace나 계측 없이 **DB 로그만으로** 어떤 API가 어떤 DB와 테이블에 접근했는지 잇습니다. 많은 기업이 PostgreSQL 로그나 pgAudit 감사 로그를 이미 SIEM으로 보내고 있다는 점을 활용합니다.

### 두 가지 DB 로그

| 로그 | 남는 곳 | 주로 쓰는 값 |
|---|---|---|
| **애플리케이션 SQL 로그** | 서비스 쪽 (예: Hibernate SQL 로거) | `timestamp`, `service`, `sql`, `request_id`, `operation_id`, `parent_hop_id`, `instance_id`, `thread`, `duration_ms` |
| **PostgreSQL 로그** | DB 쪽 (JSON 로그, pgAudit) | `application_name`, 문장 또는 pgAudit 테이블 정보 |

PostgreSQL 로그는 연결 설정에서 **Database Host·Port·Name**을 지정해 어느 DB 서버의 로그인지 알려 줍니다. `application_name`은 등록한 서비스 ID·이름·별칭과 정확히 같을 때만 그 서비스로 봅니다. 서비스마다 다른 `application_name`을 쓰는 것이 좋습니다.

### 잇는 순서

<div class="sade-steps" markdown>

1. **Request ID**로 같은 요청의 HTTP 기록과 SQL 기록을 묶습니다.
2. **SQL Operation ID**가 같으면 애플리케이션 SQL 로그와 PostgreSQL 로그의 같은 실행을 잇습니다.
3. **Parent Hop ID**로 그 SQL을 실행시킨 서비스의 요청을 구분합니다.

</div>

로그에 별도 필드를 추가하기 어려우면 SQL 앞에 주석으로 ID를 붙여도 됩니다.

```sql
/*sade request_id=9f2c1d7e4b operation_id=q-31*/ SELECT ... FROM member WHERE ...
```

HTTP 헤더나 MDC에 있는 요청 ID가 PostgreSQL 로그에 저절로 찍히지는 않습니다. 사내 공통 DB 접근 계층에서 이 값을 넣어 주어야 합니다.

### ID가 없을 때: 추정 연결

애플리케이션 SQL 로그에 ID가 없어도, 다음 조건을 **모두** 만족하면 **Inferred(추정)**로 잇고 점선으로 표시합니다.

- 같은 서비스, 같은 인스턴스(`instance_id`), 같은 스레드(`thread`)
- 그 서비스의 요청 처리 구간(`request_start`~`request_end`) 안에서 실행됨
- 그 구간에 해당하는 요청이 하나뿐임

처리 구간이 없거나, 동시에 처리 중인 요청이 여럿이거나, 인스턴스가 다르면 잇지 않습니다.

### 테이블과 저장

- SQL 구문을 SQLGlot으로 해석해 **직접 참조한 테이블**과 읽기·쓰기를 구분합니다. CTE 이름은 테이블로 세지 않고, 스키마가 없는 이름은 "미확정"으로 남깁니다.
- Parse·Bind 단계 기록은 실행으로 세지 않습니다.
- **SQL 원문, 리터럴, 파라미터, 결과 값, 에러 메시지는 수집할 때 버립니다.** 연산 종류와 테이블 이름만 남깁니다.
- SQL이 실행됐다는 기록이 데이터가 실제로 반환되었거나, 트랜잭션이 커밋되었거나, 외부로 전송되었다는 뜻은 아닙니다.

!!! warning "DB 로그를 켜기 전에"
    SADE는 DB 로깅 설정을 바꾸지 않습니다. SQL 로그는 양이 많고 파라미터에 개인정보가 들어갈 수 있으므로, 켜기 전에 로그 양과 SIEM 저장 정책을 검토하세요.

## 민감정보가 오가는 길 (Data Flow) {#data-flow}

Flows 화면의 **Sensitive Data** 버튼을 켜면, 그래프 위에 **실제 로그에서 확인한 민감정보 유형**이 표시됩니다.

| 표시 | 뜻 |
|---|---|
| 노드의 숫자 | 그 서비스의 기록 지점에서 확인한 민감정보 유형 수 |
| 선의 라벨 | 요청(부른 쪽 → 불린 쪽)과 응답(불린 쪽 → 부른 쪽) 방향을 나눠 표시 |
| 선 상세 | 필드 경로, 보낸 쪽·받은 쪽 수집 지점, 판단 이유(Field Meaning Matched / Value Format Matched) |

- **Trace를 고르면** 그 요청에서 확인한 것만 표시합니다. 다른 요청이나 다른 분기의 정보가 섞이지 않습니다.
- 명세·코드에만 있는 필드, 분류 후보, 같은 trace의 다른 곳에서 본 유형은 선에 옮겨 붙이지 않습니다.
- SQL 테이블 참조만으로는 민감정보 유형을 붙이지 않습니다.
- 본문을 수집하지 않은 곳은 **Not Collected**, 검사했지만 찾지 못한 곳은 따로 표시합니다.
- 양쪽에서 같은 유형이 보여도 **같은 값이 전달됐다는 뜻은 아닙니다.**

## 두 가지 화면

=== "요청 하나 (Trace Details)"

    Call History에서 호출을 열고 **Trace Details**를 누르면 그 요청 전용 화면이 열립니다.

    - 실제 span의 부모 관계와 실행 시간으로 **타임라인**을 그립니다.
    - span을 고르면 그 지점의 요청·응답 민감정보와 수집 정보가 나옵니다.
    - 저장된 다른 요청 예시로 바꿔 볼 수 있습니다.
    - 일부만 관측되었거나 시간 정보가 없는 구간은 그렇게 표시합니다. 요청 하나당 최대 1,000개 기록 지점까지 봅니다.

=== "전체 환경 (Flows)"

    여러 요청을 모아 **Clients → Gateways → Hosts → Destinations** 순서로 보여 줍니다.

    - **Clients**: 로그에 찍힌 호출자. IP를 고르면 그 IP의 요청 경로만 펼칩니다.
    - **Gateways**: 배포 정보, 이름, 라우팅 규칙으로 정한 게이트웨이
    - **Hosts**: 로그의 호스트 정보(`host.name`, `k8s.node.name` 등)로 묶은 서버. 없으면 "Host not observed"
    - **Destinations**: DB 로그로 확인한 PostgreSQL DB, 코드가 부르는 외부 호스트

    노드는 드래그로 옮길 수 있고 선은 노드를 피해 다시 그려집니다. 진입 API만 보이고 그 뒤를 이을 기록이 없으면 "Entry API observed"로 표시합니다.

## LOG / SPEC / CODE 전환

Flows 화면의 세 버튼은 어떤 자료로 선을 그릴지 고릅니다. 화면만 바뀌고 수집이나 스캔을 다시 하지 않습니다.

| 자료 | 원 (서비스·API) | 선 |
|---|---|---|
| LOG | 로그에서 본 API | 실제 호출, 호출자, DB 접근 |
| CODE | 코드에 있는 API | 코드의 HTTP 호출(점선), 게이트웨이 라우팅(파선) |
| SPEC | 명세에 있는 API | 없음. 명세에는 누가 부르는지가 없음 |

## 구현 범위와 확장

| | 지금 구현 | 같은 방식으로 넓히기 |
|---|---|---|
| 서비스 간 연결 | trace, hop ID, request ID | 사내 ID 필드 이름을 로그 프로필로 지정 |
| DB | PostgreSQL 로그, pgAudit, 애플리케이션 SQL 로그 | 다른 DB 로그 형식 해석기 추가 |
| 연결 정확도 | 로그에 찍힌 ID 품질에 좌우됨 | 사내 로깅 표준에 ID 전파 항목 추가 |

흐름의 정확도는 결국 **같은 요청 ID가 모든 로그에 남는지**에 달려 있습니다. 보안팀이 개발 표준으로 요청할 항목은 [기업 환경에 맞게 확장하기](extending.md#id)에 정리했습니다.

## 한계

- 대용량 SIEM 소스는 API별 샘플만 원본으로 남기므로, 흐름도 샘플 범위 안에서 보입니다([대용량 SIEM 수집](siem-collection.md)).
- 일부 서비스가 로그를 남기지 않거나 ID가 끊기면 경로가 끊겨 보입니다. 끊긴 곳은 이유와 함께 표시합니다.
- DB는 PostgreSQL을 대상으로 합니다.
- 메시지 큐, gRPC 흐름은 다루지 않습니다.
