# 민감정보 탐지 엔진

SADE는 API가 주고받는 필드가 어떤 민감정보인지 **19개 유형**으로 분류합니다. 필드 이름만 보는 방식은 `mobile`이 휴대폰 번호인지 기기 종류인지 구분하지 못하고, 값만 보는 방식은 주문번호를 전화번호로 착각합니다. SADE는 **이름, 문맥, 값의 구조**를 각각의 근거로 기록하고, 근거마다 무엇을 확인했는지 남깁니다. NLP나 LLM은 쓰지 않습니다.

## 하나의 엔진, 여러 입력

명세 선언, 코드 스캔 결과, 로그 본문, Data Types 화면의 샘플 테스트가 **모두 같은 탐지 경로**를 씁니다. 그래서 명세에서 찾은 `email`과 로그에서 찾은 `email`이 한 줄로 합쳐지고, 규칙을 바꾸면 모든 입력이 같은 규칙으로 다시 분류됩니다.

<div class="sade-pipe" markdown>
<div markdown>**위치 펼치기**<p>본문, 헤더, 쿼리, 경로 파라미터, 쿠키, 폼</p></div>
<div markdown>**후보 만들기**<p>별칭, 값 프로필, 승인된 의미, OpenAPI 힌트</p></div>

## 19개 기본 유형

=== "개인정보 (11)"

    | 유형 | 값 검증 방식 |
    |---|---|
    | NAME | 필드 의미와 문맥. 자유 문장에서 이름 추출은 하지 않음 |
    | EMAIL | 전체 문자열이 인터넷 메일 주소 형식인지 (WHATWG/RFC 문법의 ASCII 부분집합) |
    | PHONE | 국내 번호 형식 (libphonenumber KR 메타데이터 참고). 해외 번호는 미지원으로 기록 |
    | ADDRESS | 필드 의미와 문맥. 우편번호·도시 단독으로 확정하지 않음 |
    | RRN (주민등록번호) | 생년월일과 번호 구조 |
    | FOREIGN_ID (외국인등록번호) | 생년월일과 번호 구조 |
    | PASSPORT | 국내 일반 여권 M계열 구형·신형 구조 |
    | BIRTH_DATE | 생년월일 문맥 + 실제 존재하는 날짜. 미래 날짜 제외 |
    | DRIVER_LICENSE | 필드 의미 |
    | CI, DI | 필드 의미 |

=== "금융 (2)"

    | 유형 | 값 검증 방식 |
    |---|---|
    | CARD_NO | 길이 + Luhn 체크섬 (Presidio와 같은 방식) |
    | ACCOUNT_NO | 필드 의미. 은행별 번호 체계는 근거가 확보되지 않아 값 검증 안 함 |

=== "크리덴셜·시크릿 (6)"

    | 유형 | 값 검증 방식 |
    |---|---|
    | PASSWORD | 필드 의미. 길이나 복잡도는 조건이 아님 |
    | ACCESS_TOKEN, REFRESH_TOKEN | 역할이 명시된 필드, `Bearer` 파싱, JWT 구조 검사. 서명 검증은 하지 않음 |
    | API_KEY | OpenAPI `apiKey` 선언의 이름·위치, 명시적 필드. 값은 GitHub PAT 형식만 |
    | SESSION_COOKIE | 지정된 세션 쿠키 이름 (`JSESSIONID`, `PHPSESSID` 등) |
    | SECRET | 명시적 시크릿 필드, PEM/DER 개인키 구조 |

값 검증이 있는 11개 유형은 9개의 공통 검증기를 나눠 씁니다. 나머지 8개는 필드 의미로 분류합니다. 근거 없이 값 규칙을 만들어 내지 않으려는 것입니다.

## 이름과 문맥

각 유형에는 흔히 쓰는 필드 별칭이 있습니다. 예를 들어 PHONE은 `phone`, `phone_number`, `mobile`, `tel_no`, `hp_no` 등입니다. 키는 비교할 때만 정규화합니다(`phoneNumber` → `phone_number`). 원래 필드 이름과 배열 위치는 따로 보존합니다.

문맥은 필드 경로와 **같은 객체 안의 다른 필드 이름**으로 봅니다.

| 필드 | 같은 객체 | 판단 |
|---|---|---|
| `customer.name` | `email`, `phone` | 사람 문맥: NAME |
| `product.name` | `price`, `sku` | 상품 문맥: NAME 아님 |
| `server.name` | `host`, `port` | 서버 문맥: NAME 아님 |

더 가까운 상품·파일·서버 문맥이 사람 문맥보다 우선합니다. 다만 상품 문맥이라도 값이 메일 주소 형식이면 EMAIL 검사는 따로 합니다.

## 두 가지 체크: Field matched와 Value matched

| 체크 | 뜻 | 근거가 되는 입력 |
|---|---|---|
| **Field matched** | 필드 이름과 문맥이 이 유형을 가리킴 | 명세, 코드, 로그 |
| **Value matched** | 실제 값이 이 유형의 구조 검증을 통과함 | 로그의 값 |

두 체크는 서로 독립입니다. 명세의 예시 값으로 Value matched를 만들지 않습니다. 화면의 `—`는 "기록 없음"이고, 민감정보가 없다는 판정이 아닙니다.

## 근거 등급과 값 상태

HIGH / MEDIUM / LOW는 **근거의 강도**입니다. 확률이나 법적 판정이 아닙니다.

값의 상태도 구분합니다.

| 상태 | 뜻 | 집계 |
|---|---|---|
| PRESENT | 값이 있음 | 값 관측으로 셈 |
| MASKED, REDACTED | 가려진 값 (`***`, `[REDACTED]`) | 필드 의미가 분명하면 유형 집계에 넣되 값 검증은 하지 않음 |
| NULL, EMPTY | 비어 있음 | 값 관측으로 세지 않음 |
| UNKNOWN | 판단할 수 없음 | |

유형을 알 수 없는 `***` 하나만으로 민감정보를 만들지 않습니다. 값 검증이 실패했거나 형식이 맞지 않는 필드는 **Unconfirmed fields**로 따로 남깁니다.

## 검사 범위

| 한도 | 값 |
|---|---|
| 본문 크기 | 1 MiB |
| JSON 깊이 | 32 |
| 배열 항목 | 10,000 |
| 문자열 길이 | 16,384자 |
| 위치별 필드 수 | 30,000 |

한도 초과, 중복 JSON 키, 파싱 실패, 미지원 형식, 미수집은 원인 코드로 기록합니다. 모든 HTTP 상태 코드의 본문을 검사하고, 한 위치에서 오류가 나도 다른 위치는 계속 검사합니다. 자유 문장의 의미 분석, XML, 바이너리, 압축 본문은 검사 완료로 표시하지 않습니다.

!!! note "동적 키를 쓰는 응답"
    일부 응답은 데이터 자체를 객체 키로 씁니다(`{"user@example.com": {...}}`). 이런 키는 명세나 필드 목록에 그대로 저장하지 않고 가려서 남깁니다.

## 규칙 관리와 재분류

- **Policy › Rules › Data Types**에서 유형별 별칭, 승인된 필드 의미, 예외, 사용자 값 정규식을 바꿀 수 있습니다. 사용자 정규식은 전체 값 일치로 검사하며, 기본 유형의 체크섬 실패를 우회하지 않습니다.
- 규칙을 저장하면 버전이 하나 생기고, 가벼운 작업(`privacy-refresh`)이 저장된 근거로 모두 다시 분류합니다. SIEM에 다시 접속하지 않습니다.
- 결과에는 규칙 버전과 엔진 버전이 함께 남습니다. 예전 버전으로 되돌릴 수 있습니다.
- 값 검증 규칙이 바뀌어 원문이 필요한 경우에는 다시 수집해야 합니다. 원문은 저장하지 않기 때문입니다.

## 참고한 기준

이메일은 WHATWG/RFC 문법, 전화번호는 libphonenumber 한국 메타데이터, 카드번호는 Microsoft Presidio의 정규식 + Luhn 방식, 여권·외국인등록번호는 발급기관 자료, 토큰과 쿠키는 OAuth·JWT·Cookie RFC를 참고했습니다. 별칭과 문맥 규칙은 SADE의 정책이며, 학술적으로 검증된 정확도 수치를 주장하지 않습니다.
