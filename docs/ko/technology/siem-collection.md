# 대용량 SIEM 수집

기업 SIEM에는 하루에도 수백만 건의 HTTP 로그가 쌓입니다. 이걸 SADE로 전부 복사하면 SIEM을 하나 더 만드는 셈이고, 메모리와 저장 공간이 감당하지 못합니다. SADE는 **호출 수는 전부 세고, 원본은 API마다 몇 건만** 가져오는 방식으로 이 문제를 풉니다.

## 핵심 아이디어

| 알아야 하는 것 | 필요한 데이터 | SADE의 처리 |
|---|---|---|
| 어떤 API가 몇 번 호출됐나, 처음·마지막 호출, 인증 방식 비율, Shadow API | 모든 호출의 **개수** | 전체를 읽으며 집계만 저장 |
| 실제 요청이 어떤 모양이었나, 명세와 다른 필드, 민감정보 값, 요청 하나의 경로 | 몇 건의 **원본** | API·상태별 최근 요청 몇 개만 저장 |

원본 로그는 SIEM에 그대로 있습니다. SADE는 판단에 필요한 만큼만 가져갑니다.

### 1. 구간으로 나누고 한 줄씩 읽기

수집 기간(예: 최근 7일)을 60분 구간으로 나누고, 구간마다 Splunk export 검색을 한 번 보냅니다. 응답은 받는 대로 한 줄씩 처리해서, 응답 전체를 메모리에 올리지 않습니다. 그래서 응답 크기 한도가 없습니다.

### 2. 몰린 구간은 저절로 쪼개기

트래픽은 고르지 않습니다. 평소엔 한 시간에 수천 건인데 이벤트나 장애 때는 몇 분에 수만 건이 몰립니다. 한 구간에서 5만 건을 넘게 읽으면 그 구간을 멈추고 반으로 나눠 다시 읽습니다. 최소 1분까지 나눕니다. 그래서 몰린 정도와 상관없이 메모리에 두는 이벤트는 약 5만 건으로 묶입니다.

!!! info "쪼갠 구간은 파싱하지 않습니다"
    구간을 다 읽은 뒤에 한 번에 파싱합니다. 중간에 쪼개기로 한 구간은 파싱 비용을 쓰지 않고 버립니다.

### 3. 구간 경계에서 요청이 갈라지지 않게

게이트웨이 로그와 서비스 로그는 같은 요청인데 시각이 조금 다릅니다. 하나는 10:59:59.9, 다른 하나는 11:00:00.1이면 서로 다른 구간에 들어가서 **한 호출이 두 번 세집니다.**

SADE는 구간 끝 60초 안에 이벤트가 하나라도 있는 요청을 **그 요청의 이벤트 전체와 함께** 다음 구간으로 넘깁니다. 다음 구간에서 짝과 만나 한 호출로 합쳐집니다. 범위의 마지막 구간은 모두 셉니다.

=== "보류 없이"

    | 이벤트 | 시각 | 들어간 구간 | 결과 |
    |---|---|---|---|
    | 서비스 로그 | 10:59:59.8 | 10시 구간 | 1건 |
    | 게이트웨이 로그 | 11:00:00.1 | 11시 구간 | 1건 |
    | | | | **2건으로 셈 (틀림)** |

=== "보류했을 때"

    | 이벤트 | 시각 | 처리 | 결과 |
    |---|---|---|---|
    | 서비스 로그 | 10:59:59.8 | 같은 요청에 끝 60초 이벤트가 있어 보류 | |
    | 게이트웨이 로그 | 11:00:00.1 | 11시 구간에서 보류된 짝과 합침 | |
    | | | | **1건으로 셈** |

### 4. 집계와 샘플로 나눠 저장

구간을 읽으면 분석 단계와 **똑같은 규칙**으로 이벤트를 서비스에 배정하고, 같은 요청의 게이트웨이·서비스 이벤트를 한 호출로 합칩니다. 그다음 두 가지를 만듭니다.

**집계 항목**
: (서비스, 메서드, 경로 모양, 상태 코드, 인증 방식, 호출자 …)마다 하나씩 만듭니다. 호출 수, 처음·마지막 호출 시각을 담습니다. 경로 모양은 `/orders/1024`, `/orders/77`을 `/orders/{id}`로 묶은 것이라 항목 수가 크게 늘지 않습니다.

**샘플**
: (서비스, 메서드, 경로 모양, 상태 코드)마다 요청 5개의 원본을 남깁니다. 최근 구간을 먼저 고르고, 같은 구간 안에서는 **요청 ID의 해시값이 작은 순서**로 고릅니다. 해시는 어느 로그에서 계산해도 같으므로, 게이트웨이 로그에서 고른 요청과 서비스 로그에서 고른 요청이 저절로 같아집니다. 그래서 샘플에서도 요청 하나의 경로가 끊기지 않습니다.

### 5. 분석에서 두 가지를 다르게 다루기

| 항목 | 호출 수, 인증 통계 | Call History, 명세 점검, 민감정보 값, Flows |
|---|---|---|
| 집계 항목 | `_count`만큼 셈 | 쓰지 않음 |
| 샘플 원본 | 세지 않음 (집계에 이미 포함) | 씀 |

이렇게 해야 같은 호출을 두 번 세지 않으면서 화면의 숫자는 전체 기준으로 맞습니다.

### 6. 체크포인트와 이어 읽기

- 구간을 마칠 때마다 "여기까지 읽음"을 기록합니다. 다음 수집은 그 지점부터 읽어서 같은 구간을 두 번 세지 않습니다.
- 중간 구간이 실패하면 마친 구간까지 저장하고 상태를 Partial로 둡니다. 다음 수집이 실패한 구간부터 이어 읽습니다. 첫 구간부터 실패하면 이전 자료를 그대로 둡니다.
- 경계에서 보류한 이벤트가 있으면 체크포인트는 보류선(구간 끝 60초 전)에 멈춥니다. 수집이 그 자리에서 끝나도 다음 수집이 보류한 이벤트를 다시 읽습니다.
- Latest가 `now`이면 지금보다 5분 전까지만 읽습니다. 색인이 늦게 끝난 이벤트를 다음 수집에서 읽기 위해서입니다. 5분보다 더 늦게 색인된 이벤트는 놓칠 수 있습니다.

## 검증

"집계 + 샘플"로 계산한 결과가 "모든 이벤트를 저장"한 결과와 같은지, 같은 로그로 두 번 계산해 비교했습니다.

| 데이터 | 비교 항목 | 차이 |
|---|---|---|
| YAS 로그 16,000건 | API별 호출 수, 처음·마지막 호출, 인증 통계, Shadow API, 호출 합계와 성공·오류 수 | 0건 (저장 후 다시 읽어도 0건) |
| YAS 로그 60,000건, 구간 분할 강제 | 위와 같음 (API 209개, 호출 33,474건) | 0건 |

대용량은 같은 형식으로 응답하는 로컬 HTTPS export 서버에 YAS 로그 232,292건(104 MB)을 넣어 확인했습니다.

| | 이전 방식 (한 번에 받기) | 구간 수집 |
|---|---|---|
| 결과 | 10 MB 초과로 실패 | 94개 구간 모두 수집 |
| 저장 | | 호출 130,402건, API 209개, 배치 8.4 MB |
| 최대 메모리 | | 약 380 MB |
| 같은 범위 재수집 | | 새 구간 0개, 0.3초, 숫자 변화 없음 |

## 한계

- Call History 목록, 명세 점검, 값 기반 민감정보 탐지, Flows는 **샘플 기준**입니다. 1만 건 중 1건만 다른 필드를 보내는 드문 경우는 놓칠 수 있습니다.
- 원본을 전부 받아서 SADE에서 셉니다. 하루 수억 건 규모에서는 전송량이 커서, SIEM에서 먼저 집계하는 방식을 다음 단계로 검토하고 있습니다.
- App log와 Trace 소스는 짝짓기에 모든 이벤트가 필요해서 집계하지 않고 전부 저장합니다(최대 200,000건).
- 실제 기업 Splunk 서버에서의 검증은 진행 중입니다.
