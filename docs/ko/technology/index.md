# 방법론 개요

SADE의 방법론은 하나의 질문에서 출발합니다. **"이미 회사에 있는 자료만으로 API 자산과 개인정보 흐름을 얼마나 정확하게 다시 그릴 수 있는가."** 새 장비나 에이전트를 들이는 대신, 로그·명세·코드를 같은 API 단위로 맞추고 서로의 빈 곳을 메우는 방식입니다.

각 방법론은 독립된 문제를 풉니다. 기업마다 가진 자료가 다르므로, 필요한 방법만 골라 적용하거나 일부를 사내 환경에 맞게 바꿔 쓸 수 있습니다.

## 전체 흐름

<div class="sade-pipe" markdown>
<div markdown>**수집**<p>SIEM·데이터 레이크의 로그, 저장소의 코드, 명세</p></div>
<div markdown>**정규화**<p>형식이 다른 로그를 하나의 형태로</p></div>

<div markdown>**저장**<p>실제 값은 지우고 결과만</p></div>
</div>

## 문제별 방법론

| 보안 문제 | 방법론 | 입력 |
|---|---|---|
| 로그 형식이 회사·장비마다 달라 분석을 시작할 수 없음 | [로그 정규화와 필드 감지](log-normalization.md) | 로그 |
| SIEM에 쌓인 대량 로그를 분석 도구로 옮기기 어려움 | [대용량 SIEM 수집](siem-collection.md) | 로그 |
| 명세에 없는 API(Shadow API)를 알 수 없음 | [API 식별과 Shadow API](api-discovery.md) | 로그 + 명세 + 코드 |
| 어떤 API가 개인정보를 주고받는지 모름 | [민감정보 탐지](sensitive-data.md) | 로그 + 명세 + 코드 |
| 명세가 없거나 오래됨 | [code2spec](code2spec.md) | 코드 |
| 로그에 안 남은 서비스 간 호출, DB 접근을 모름 | [code2flow](code2flow.md) | 코드 |
| 요청 하나가 어느 서비스와 DB를 거쳤는지 추적이 안 됨 | [런타임 흐름 복원](runtime-flow.md) | 로그 |
| 명세와 다르게 데이터가 나가거나 인증 없이 성공하는 호출 | [호출별 명세 점검](spec-check.md) | 로그 + 명세 |
| 분석 도구 자체가 개인정보 저장소가 되는 위험 | [값을 남기지 않는 저장](value-free-storage.md) | 전체 |

## 세 가지 입력이 서로 메우는 것

| 입력 | 알 수 있는 것 | 알 수 없는 것 | 빈 곳을 메우는 입력 |
|---|---|---|---|
| **로그** | 실제 호출, 횟수, 인증 방식, 주고받은 필드 | 수집 기간 밖의 호출, 남지 않은 본문 | 코드(호출 가능한 경로), 명세(필드 정의) |
| **명세** | 약속한 요청·응답 형식 | 실제로 호출되는지, 구현되어 있는지 | 로그(실제 호출), 코드(구현 여부) |
| **코드** | 구현된 API, 호출하는 서비스, DB 접근 | 실제로 실행되는지, 얼마나 자주인지 | 로그(실행 여부와 횟수) |

어느 입력에서 확인했는지는 모든 API와 필드에 `Spec` / `Code` / `Log`로 남깁니다. 확인할 자료가 없으면 "없음"이 아니라 "미확인"이나 "Not evaluated"로 표시합니다.

## 참조 구현과 확장

각 방법론 페이지 끝의 **구현 범위와 확장**에 이번 구현이 다루는 범위와, 같은 방식으로 넓히는 방법을 적었습니다. 확장 지점을 한곳에 모은 내용은 [기업 환경에 맞게 확장하기](extending.md)에 있습니다.

## 원칙

- **추측하지 않습니다.** 이을 후보가 여럿이면 잇지 않고, 경로를 알 수 없으면 "미확정"으로 남깁니다.
- **실행하지 않습니다.** 코드는 읽기만 하고, 서비스에 요청을 보내지 않습니다.
- **값을 남기지 않습니다.** 판단에 필요한 처리는 메모리에서 끝내고, 저장할 때는 타입과 판단 결과만 남깁니다.
- **다시 계산할 수 있습니다.** 규칙을 바꾸면 저장된 결과로 다시 분석할 수 있고, 같은 입력에서는 같은 결과가 나옵니다.
