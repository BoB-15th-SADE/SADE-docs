# API 식별

코드, 명세, 로그는 같은 API를 서로 다르게 적습니다. 코드는 `/orders/{orderId}`, 명세는 `/shop/orders/{id}`, 로그는 `/api/shop/orders/1001`처럼 남습니다. 매퍼는 아래 순서로 이 셋을 한 API로 합칩니다.

## 1. 서비스 이름 맞추기

| 출처 | 서비스 이름을 가져오는 곳 |
|---|---|
| 코드 | 코드 스캔이 찾은 서비스 이름(`spring.application.name` 등) |
| 명세 | 명세를 등록할 때 넣은 Service |
| 로그 | `service.name` 필드, 없으면 서비스 이름 규칙이나 `host.name` |

<div class="sade-steps" markdown>

1. 글자가 그대로 같으면 같은 서비스입니다.

2. 다르면 [Settings](../policy/access-scope.md#settings)에서 합친 이름으로 바꿔 다시 비교합니다.

3. 그래도 다르면 다른 서비스입니다.

</div>

대소문자나 `-service` 같은 꼬리말은 추측해서 지우지 않습니다. `order-service`와 `orders`가 같은 서비스라면 Settings에서 합칩니다. 화면에 나오는 서비스 이름은 코드, 명세, 로그 순서로 고릅니다.

## 2. 경로 틀 만들기

API는 `서비스:메서드:경로 틀`로 구분합니다. 경로 틀은 아래 순서로 만듭니다.

<div class="sade-steps" markdown>

1. 쿼리 문자열(`?` 뒤)을 뗍니다.

2. 값 자리를 `{}`로 바꿉니다. 코드와 명세, 로그의 규칙이 다릅니다.

3. 끝 슬래시를 뗍니다. `/api/orders/`와 `/api/orders`는 같은 API입니다. 루트 `/`는 그대로 둡니다.

4. 대소문자는 바꾸지 않습니다.

</div>

값 자리를 바꾸는 규칙

| 출처 | `{}`로 바꾸는 구간 | 예 |
|---|---|---|
| 코드, 명세 (선언) | `{이름}`으로 선언한 구간만. 숫자여도 고정 구간은 그대로 | `/reports/2024`와 `/reports/{year}`는 다른 API |
| 로그 (관측) | 숫자, UUID, 긴 16진수, 숫자가 섞인 긴 토큰, 영문 대문자와 숫자가 섞인 코드, 숫자와 구분자로만 된 구간 | `/orders/1001` → `/orders/{}`, `/download/9f8a7b6c5d4e3f2a1b0c` → `/download/{}` |

로그는 실제 값이 찍히기 때문에 값 모양 구간을 묶습니다. 같은 자리에 값 종류가 많으면(기본 20개 초과, `SADE_LOG_ID_MIN_VALUES`) 값 모양이 아니어도 `{id}`로 봅니다.

경로 대소문자를 구분하지 않는 서비스는 `.env`의 `SADE_PATH_CASE_INSENSITIVE_SERVICES`에 넣습니다.

## 3. context path 붙이기

코드의 경로는 Controller에 적힌 경로입니다. 서비스 앞에 붙는 context path(예: `/shop`)는 설정에 따로 있습니다.

- 코드: 스캔이 찾은 context path를 Controller 경로 앞에 붙입니다.
- 명세: `servers[].url`의 경로 부분을 `paths` 앞에 붙입니다. `http://host/shop`과 `/orders`는 `/shop/orders`가 됩니다.

그래서 코드 `/orders`(context path `/shop`)와 명세 `/orders`(servers `/shop`)가 같은 API로 맞습니다.

## 4. 로그 경로를 코드, 명세 API에 붙이기

같은 서비스, 같은 메서드 안에서 구간마다 비교합니다.

<div class="sade-steps" markdown>

1. 고정 구간이 글자 그대로 같은 API를 먼저 찾습니다. 로그의 `{}`는 선언의 `{}`, 또는 값 모양인 고정 구간과 맞습니다.

2. 없으면 선언의 `{}` 자리가 로그의 어떤 값과도 맞는 것으로 봅니다. 예: 로그 `/products/iphone-15`를 선언 `/products/{slug}`에 붙임

3. 맞는 API가 여럿이면(`/reports/2024`와 `/reports/{year}`) 원본 로그로 나눠 셉니다. 경로가 정확히 같은 호출은 고정 경로로, 나머지는 `{}` 쪽으로 붙입니다.

4. 맞는 것이 없으면 로그에서만 보인 API가 됩니다.

</div>

- 고정 경로가 먼저입니다. `/products/new`와 `/products/{slug}`가 함께 있으면 로그 `/products/new`는 고정 경로로 갑니다.
- 고정 구간이 하나도 없는 선언(`/{slug}`, `/{a}/{b}`)에는 2번 규칙을 쓰지 않습니다. 이런 선언에 `/admin`, `/actuator` 같은 호출이 붙으면 Shadow 신호가 사라지기 때문입니다.
- 구간 수가 다른 경로는 맞지 않습니다(`/files/{name}`과 `/files/a/b`).

## 5. 게이트웨이를 거친 경로 바꾸기

게이트웨이 앞에서 찍힌 로그는 바깥 경로(예: `/api/cart/items`)로 남고, 서비스 코드는 안쪽 경로(`/items`)를 씁니다. 4번에서 맞는 API가 없을 때만 아래 순서로 바꿔 봅니다.

| 순서 | 근거 | 예 |
|---|---|---|
| 1 | 사람이 넣은 게이트웨이 경로 규칙(`gateway_rules` 설정) | `/api/cart` → cart-service의 `/` |
| 2 | 코드 스캔이 읽은 게이트웨이 라우트(Route maps)의 경로 조건과 바꾸기 규칙 | Spring Cloud Gateway 라우트의 `Path=/api/cart/**` 조건과 경로를 바꾸는 필터 |

바꾼 경로로 API를 찾으면 합치고, 바꾸기 전 경로는 API 상세에 외부 경로로 남깁니다.

`gateway_rules`는 설정 API로만 넣을 수 있습니다. 현재 Settings 화면에는 입력 칸이 없습니다. 코드에 게이트웨이가 없으면 게이트웨이 앞 경로로 찍힌 로그가 Shadow로 보일 수 있습니다.

## 6. 게이트웨이, BFF가 찍은 줄을 주인 서비스로 넘기기

같은 요청이 게이트웨이 로그와 서비스 로그에 모두 찍힙니다. 게이트웨이 줄이 따로 API가 되면 정상 API가 가짜 Shadow로 보입니다. 게이트웨이 자기 서비스에서 맞는 API가 없을 때 아래 순서로 처음 맞는 근거 하나를 씁니다.

<div class="sade-steps" markdown>

1. 사람이 넣은 게이트웨이 경로 규칙이 맞으면 그 규칙의 서비스로 넘깁니다.

2. 코드의 게이트웨이 라우트 조건이 맞으면 그 라우트가 가리키는 서비스로 넘깁니다.

3. 그 서비스가 로그에서 실제로 부른 서비스 가운데, 같은 메서드와 같은 경로의 API가 정확히 한 서비스에 하나 있으면 그 API로 넘깁니다.

</div>

- 호출 수는 두 번 세지 않습니다. 주인 API에 자기 로그 호출이 있으면 그 수만 씁니다.
- 넘겨받은 줄의 출발지 IP, 민감 유형은 주인 API에 합칩니다.
- 3번은 같은 경로와 실제 호출 선을 합친 추론입니다. BFF가 같은 경로로 자기 API를 가지면 틀리게 합쳐질 수 있습니다. BFF 명세를 올리면 BFF 자기 API로 먼저 잡힙니다.

## 7. 명세 상태 정하기

위에서부터 처음 맞는 것 하나를 고릅니다. 여기서 명세는 기업이 등록한 명세만 뜻합니다. 코드에서 만든 명세는 세지 않습니다.

| 순서 | 상태 | 조건 |
|---|---|---|
| 1 | Documented | 등록한 명세에 있음 |
| 2 | Shadow | 그 서비스에 코드나 명세가 있는데, 이 API는 로그에만 있음. 응답이 모두 404나 405면 제외 |
| 3 | Undocumented | 그 서비스에 명세가 있는데, 이 API는 코드에만 있음 |
| 4 | No Spec | 그 서비스에 비교할 코드나 명세가 없음 |

로그만 넣은 서비스의 API는 모두 No Spec입니다. Shadow를 보려면 그 서비스의 코드나 명세가 필요합니다.

## 8. 인증 선언 요약

| 출처 | 값 |
|---|---|
| 코드 | 접근 제어 선언이 하나 이상 있으면 "선언됨", 없으면 "모름". 선언이 없다고 인증이 없다고 보지 않습니다 |
| 명세 | operation이나 문서 전체 `security`가 있으면 "선언됨", 빈 배열이거나 없으면 "선언 없음" |
| 로그 | 늘 "모름". 로그에 인증 헤더를 남기지 않습니다 |

목록과 필터는 두 출처를 합친 요약 하나를 씁니다.

| 요약 | 조건 |
|---|---|
| 충돌 | 코드와 명세가 모두 판정했는데 서로 다름 |
| 필요 | 판정한 출처가 모두 "선언됨" |
| 없음 | 판정한 출처가 모두 "선언 없음" |
| 모름 | 판정한 출처가 없음 |

충돌은 관리 우선순위의 H 신호가 됩니다. 모두 선언 근거이며, 요청이 실제로 막히는지는 확인하지 않습니다.
