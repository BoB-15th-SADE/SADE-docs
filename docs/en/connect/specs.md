# OpenAPI specifications

Register a service and specification to inspect declared APIs, fields and sensitive-field candidates before collecting traffic. Supported uploads are **OpenAPI 3.0 / 3.1 JSON, up to 10 MB**.

## Quick setup

1. Open **Connect → Specifications → Add service**.
2. Select an OpenAPI JSON file. Available names and server details prefill the form.
3. Review Name, ID, Base URL and Path prefix.
4. Choose **Save**.
5. Inspect **APIs → Inventory**. Sensitive-field classification updates in the background.

| Setting | Meaning |
|---|---|
| Name | Display name |
| ID | Service identifier for log assignment and code mapping |
| Base URL | API server address |
| Path prefix | Prefix present in calls but absent from specification paths |
| OpenAPI file | Optional; register a service first and attach a specification later. |

For a called path `/orders/items` and specification path `/items`, set the prefix to `/orders`. Do not guess mappings between unrelated paths.

## Specification origins

| Label | Origin |
|---|---|
| Active / File upload | User-provided specification |
| From code | Generated by a GitHub scan |
| No spec | Service-only registration or traffic discovery |
| Inferred draft | Draft generated from observed traffic structure |

A traffic-derived draft is not an independent contract. Relevant specification checks remain Not evaluated to avoid assessing traffic against a baseline generated from that same traffic.

## Combine specifications and code

GitHub rescans preserve uploaded specifications and retain the generated code specification separately. Use a [route map](code.md) to connect public gateway paths to different backend implementation paths.

**Field matched** on a declaration is not proof of a transmitted value. Specification examples do not produce sensitive-value observations.
